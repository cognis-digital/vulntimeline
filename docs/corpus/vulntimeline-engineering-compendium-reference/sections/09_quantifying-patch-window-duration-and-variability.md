## 9. Quantifying Patch-Window Duration and Variability

### Defining the Patch-Window Metric

The patch-window metric is a quantitative measure that defines the period during which a vulnerability remains unpatched after its public disclosure. It serves as a critical indicator of the time window during which an attacker can exploit a known vulnerability before a patch becomes available. This metric is essential for assessing the risk associated with vulnerabilities, as it directly correlates with the potential impact of exploitation. The patch-window duration can vary significantly across different systems, software, and organizations, depending on factors such as the complexity of the software, the response time of vendors, and the adoption rate of patches by users. To accurately define the patch-window metric, we must consider both its temporal and contextual dimensions, including the mechanisms that govern its calculation and the factors that influence its variability.

The foundation of the patch-window metric lies in the timeline of vulnerability disclosure and patching. The process typically begins with the public disclosure of a vulnerability, which marks the start of the patch-window period. This disclosure is often accompanied by the release of a detailed technical description, including proof-of-concept code or exploit details, enabling attackers to develop exploits. Following this, the vendor or software maintainer issues a patch or update to address the vulnerability. The time between the disclosure and the availability of the patch defines the duration of the patch-window. However, the actual period during which the vulnerability is exploitable may extend beyond this, as it depends on how quickly users apply the patch and whether the patch is effective in mitigating the vulnerability.

To define the patch-window metric rigorously, we must establish a clear framework for its calculation. One widely used approach is to measure the time between the publication of a vulnerability report and the release of the corresponding patch. This method provides a straightforward, albeit simplified, view of the patch-window duration. However, it does not account for the time it takes for users to apply the patch or the time required for the patch to be integrated into their systems. To refine this metric, we can incorporate additional factors such as the time between patch release and user adoption, which is influenced by the size of the user base, the complexity of the software ecosystem, and the availability of update mechanisms.

A more comprehensive definition of the patch-window metric would involve integrating both the vendor's response time and the user's patching behavior. This approach acknowledges that the patch-window is not solely determined by the vendor but also by the users' ability to apply patches promptly. Therefore, the metric should be calculated as the time between the vulnerability disclosure and the point at which a majority of users have applied the patch, or until the vulnerability is effectively mitigated through alternative means such as workarounds or configuration changes. This definition allows for a more accurate representation of the actual risk exposure associated with a vulnerability.

To operationalize the patch-window metric, we can employ a combination of data sources, including vulnerability databases, software update logs, and user adoption statistics. For example, the National Vulnerability Database (NVD) provides detailed information on vulnerability disclosures, including the date of publication and the date of the first patch release. By analyzing these dates, we can compute the initial patch-window duration. However, to capture the full extent of the patch-window, we must also consider user adoption data, which may be obtained from telemetry systems, enterprise software management platforms, or public repositories such as GitHub. These sources allow us to track when patches are deployed across different user environments and calculate the time between patch availability and user application.

One notable example of this approach is the analysis of the Heartbleed vulnerability (CVE-2014-0160), which exposed a critical flaw in the OpenSSL cryptographic library. The vulnerability was disclosed on April 7, 2014, and the first patch was released on April 8, 2014. However, the patch-window duration extended well beyond this period, as many organizations took weeks or even months to apply the patch. This discrepancy highlights the importance of incorporating user adoption data into the patch-window metric. In this case, the actual patch-window duration could be measured in months, depending on the time it took for users to deploy the patch and ensure its effectiveness.

Another example is the SolarWinds Orion vulnerability (CVE-2020-14882), which was disclosed in November 2020. The initial patch was released shortly after the disclosure, but the patch-window duration was influenced by the complexity of the SolarWinds software ecosystem and the widespread use of its products across enterprises. The patch required coordination between multiple stakeholders, including the vendor, users, and third-party integrators, leading to a prolonged patch-window period. This case underscores the variability in patch-window durations and the need for a metric that accounts for both vendor response times and user adoption behaviors.

In addition to these examples, the patch-window metric can be further refined by incorporating the concept of "patching lag," which refers to the time between the release of a patch and its deployment across the user base. This lag is influenced by factors such as the size of the user base, the availability of automated update mechanisms, and the urgency of the vulnerability. For instance, a critical vulnerability in a widely used operating system like Windows may have a shorter patching lag due to the presence of automatic updates, whereas a less common software component may experience a longer lag due to manual update processes.

The variability of the patch-window metric is further influenced by the type of vulnerability and its impact. High-severity vulnerabilities, such as those rated as Critical or High in the Common Vulnerability Scoring System (CVSS), tend to have shorter patch-window durations due to the urgency of their remediation. Conversely, low-severity vulnerabilities may have longer patch-window durations as they are often deprioritized for patching. This variability is evident in the analysis of vulnerabilities across different software ecosystems, where high-impact vulnerabilities receive more attention and quicker responses from vendors.

In conclusion, the patch-window metric is defined by the period during which a vulnerability remains unpatched after its public disclosure. It is influenced by both the vendor's response time and the user's ability to apply patches promptly. To accurately define this metric, we must integrate data sources such as vulnerability databases, software update logs, and user adoption statistics. By considering factors such as patching lag, vulnerability severity, and user base size, we can develop a more comprehensive understanding of the patch-window duration and its variability. The examples of Heartbleed and SolarWinds illustrate the importance of this metric in assessing risk exposure and highlight the need for a robust framework that captures both vendor and user behaviors in the patching process.

### Temporal Granularity and Resolution in Patch-Window Analysis

Temporal Granularity and Resolution in Patch-Window Analysis

Temporal granularity refers to the level of detail with which events are recorded or analyzed over time, while temporal resolution denotes the smallest interval at which data can be measured or observed. In the context of patch-window analysis, these concepts are critical for accurately capturing the dynamics of vulnerability disclosure and remediation. The granularity and resolution of temporal data directly influence the precision of patch-window metrics, which in turn affect the reliability of risk assessments and the effectiveness of mitigation strategies.

The granularity of temporal data is often determined by the frequency at which events are logged or reported. For instance, in software ecosystems, vulnerability disclosures are typically timestamped with high precision—often down to the second—by entities such as the National Vulnerability Database (NVD) or the Common Vulnerabilities and Exposures (CVE) system. These timestamps allow for precise tracking of when a vulnerability is first disclosed, when patches are released, and when patches are applied by users or organizations. However, the granularity of these timestamps may vary depending on the source. For example, some internal systems might log events at the minute level, while others may record them in hours or even days. This variability can introduce inconsistencies in patch-window analysis, especially when comparing across different platforms or organizations.

Temporal resolution, on the other hand, refers to the smallest time interval that can be reliably measured or analyzed. In patch-window analysis, this is often constrained by the availability and accuracy of data sources. For example, if a vulnerability disclosure is recorded only at the daily level, the analysis will lack the ability to capture short-term fluctuations in patch deployment or user behavior. Conversely, high-resolution data—such as minute-level timestamps—can reveal subtle patterns in patch adoption, such as spikes in activity during specific hours of the day or around key release events.

The interplay between granularity and resolution is particularly evident when analyzing patch windows across different software ecosystems. For instance, in open-source projects like Linux or Apache, vulnerabilities are often disclosed with high temporal granularity, allowing for detailed analysis of the time between disclosure and patching. In contrast, proprietary systems may have less granular data due to internal logging practices or delayed disclosure processes. This disparity can lead to significant variations in the calculated patch-window durations, even when comparing similar vulnerabilities across platforms.

To illustrate this, consider the case of the Heartbleed vulnerability (CVE-2014-0160), which affected OpenSSL and was disclosed on April 7, 2014. The NVD logged the disclosure at a precise timestamp, allowing for accurate tracking of the patch window. However, in some enterprise environments, the deployment of patches may have been recorded only at the daily level, leading to an overestimation of the patch window duration. This discrepancy highlights the importance of aligning temporal granularity across data sources to ensure consistency in patch-window analysis.

Another example is the WannaCry ransomware attack, which exploited a vulnerability in Microsoft Windows (CVE-2017-0144). The patch was released on March 14, 2017, but many organizations delayed application of the patch due to various constraints. The temporal resolution of patch deployment data varied widely; some systems recorded patch application at the minute level, while others only logged it daily. This variation in resolution affected the accuracy of patch-window metrics, as the exact timing of patch adoption was critical in determining the vulnerability’s impact.

Temporal granularity and resolution also play a role in the analysis of user behavior within the patch window. For instance, in enterprise environments, the timing of patch deployment can be influenced by factors such as system uptime, maintenance windows, and organizational policies. High-resolution data allows for the identification of these patterns, enabling more precise modeling of patch adoption. Conversely, lower resolution data may obscure these nuances, leading to less accurate predictions of future patch behavior.

The choice of temporal granularity and resolution also depends on the specific goals of the analysis. For instance, if the objective is to assess the overall risk exposure of an organization, a coarser granularity may be sufficient, as long as it captures the general trend of vulnerability remediation. However, if the goal is to optimize patching schedules or identify bottlenecks in the deployment process, higher granularity becomes essential. This distinction underscores the need for tailoring temporal parameters to the specific requirements of the analysis.

In addition to the technical aspects of granularity and resolution, their impact on patch-window analysis is also influenced by the data sources used. For example, the NVD provides standardized timestamps for vulnerabilities, ensuring a consistent level of granularity across different entries. However, when integrating data from multiple sources—such as internal logs, third-party tools, or user feedback—the variability in temporal precision can introduce noise into the analysis. To mitigate this, analysts often employ data normalization techniques, such as aligning timestamps to a common reference point or applying interpolation methods to fill gaps in low-resolution data.

The importance of temporal granularity and resolution is further emphasized by the need for reproducibility in patch-window analysis. High granularity ensures that results can be consistently replicated across different studies or organizations, while high resolution allows for more detailed insights into the dynamics of vulnerability remediation. This is particularly important in academic research or industry benchmarks, where the ability to compare findings across different contexts is crucial.

In conclusion, temporal granularity and resolution are fundamental to the accuracy and reliability of patch-window analysis. The level of detail captured by these factors directly influences the precision of metrics such as patch-window duration, variability, and risk exposure. By carefully selecting and aligning temporal parameters, analysts can ensure that their findings are both consistent and actionable, ultimately contributing to more effective vulnerability management strategies.

### Statistical Distribution of Patch-Window Durations

The statistical distribution of patch-window durations is a critical component in quantifying the variability and predictability of software update cycles. To understand this distribution, it is essential to analyze how patch windows are structured across different software ecosystems and how they vary based on factors such as product type, vendor practices, and system complexity. The distribution of these durations can be modeled using various statistical techniques, including probability distributions like the exponential, Weibull, and normal distributions. These models help in identifying patterns, predicting future patch-window behavior, and assessing the risk associated with extended or inconsistent patch windows.

One of the most commonly observed distributions in patch-window data is the exponential distribution. This distribution is particularly useful for modeling events that occur randomly over time, such as the time between software updates. The exponential distribution is characterized by a single parameter, λ (lambda), which represents the rate at which events occur. In the context of patch windows, λ can be interpreted as the average number of updates per unit time. The probability density function (PDF) of the exponential distribution is given by:

$$ f(t) = \lambda e^{-\lambda t} $$

where $ t $ is the time until an event occurs. This distribution is memoryless, meaning that the probability of an update occurring in the next time interval does not depend on how long it has been since the last update. This property makes the exponential distribution well-suited for modeling patch windows where updates are relatively independent and occur at a constant average rate.

Empirical studies have shown that the exponential distribution can be a reasonable approximation for patch-window durations in certain software ecosystems. For example, in the case of open-source projects like Linux distributions, the patch windows for security updates are often consistent and predictable. This predictability aligns with the properties of the exponential distribution, where the average time between updates is relatively stable. However, it is important to note that the exponential distribution may not capture all aspects of patch-window variability, particularly in cases where updates are influenced by external factors such as vendor schedules or system dependencies.

Another commonly used distribution for modeling patch-window durations is the Weibull distribution. Unlike the exponential distribution, the Weibull distribution allows for varying failure rates over time, making it more flexible in capturing different patterns of update behavior. The Weibull distribution is characterized by two parameters: a shape parameter $ k $ and a scale parameter $ \lambda $. The PDF of the Weibull distribution is given by:

$$ f(t) = \frac{k}{\lambda} \left( \frac{t}{\lambda} \right)^{k-1} e^{-\left( \frac{t}{\lambda} \right)^k} $$

The shape parameter $ k $ determines the behavior of the failure rate over time. When $ k < 1 $, the failure rate decreases over time, which could correspond to a situation where patch windows become shorter as the software matures. When $ k = 1 $, the Weibull distribution reduces to the exponential distribution, indicating a constant failure rate. When $ k > 1 $, the failure rate increases over time, which might be observed in systems where patch windows become longer due to increasing complexity or resource constraints.

Empirical analysis of patch-window data from various software ecosystems has shown that the Weibull distribution can provide a more accurate fit than the exponential distribution in certain cases. For instance, in commercial software such as Microsoft Windows, the patch windows for security updates have been observed to exhibit increasing variability over time. This trend suggests that the failure rate (in this case, the rate at which patches are released) may be increasing, which is consistent with a Weibull distribution where $ k > 1 $. The ability of the Weibull distribution to capture such trends makes it a valuable tool for modeling patch-window durations in more complex and dynamic environments.

In addition to the exponential and Weibull distributions, the normal distribution is also frequently used to model patch-window durations. The normal distribution is characterized by its mean $ \mu $ and standard deviation $ \sigma $, and it is symmetric around the mean. This property makes the normal distribution suitable for modeling situations where patch windows are influenced by a combination of factors that tend to balance out over time. For example, in enterprise software systems where multiple stakeholders are involved in the update process, the patch-window durations may exhibit a normal distribution due to the averaging effect of various contributing factors.

The normal distribution can be particularly useful when analyzing large datasets of patch-window durations, as it provides a clear and interpretable measure of central tendency and variability. The mean of the distribution represents the average patch-window duration, while the standard deviation quantifies the spread of durations around the mean. In practice, this allows for the identification of outliers or anomalies in the data, which could indicate issues such as delayed patches or inconsistent update schedules.

However, the normal distribution has limitations when applied to patch-window data. For instance, it assumes that the data is symmetric and does not account for skewness or heavy-tailed behavior, which may be present in certain software ecosystems. In cases where patch windows are influenced by rare but significant events (such as major security breaches or system outages), the normal distribution may not provide an accurate representation of the underlying distribution.

To address these limitations, researchers have explored alternative distributions such as the log-normal and gamma distributions. The log-normal distribution is particularly useful for modeling data that is skewed to the right, which can occur when patch windows are influenced by factors that tend to increase the duration over time. The gamma distribution, on the other hand, is flexible and can accommodate a wide range of shapes depending on its parameters, making it suitable for modeling complex patch-window behaviors.

In conclusion, the statistical distribution of patch-window durations plays a crucial role in quantifying the variability and predictability of software update cycles. By analyzing the data through the lens of probability distributions such as the exponential, Weibull, and normal distributions, researchers can gain valuable insights into the behavior of patch windows across different software ecosystems. Each distribution offers unique advantages and limitations, and their application depends on the specific characteristics of the data and the underlying factors influencing patch-window durations. The choice of distribution ultimately depends on the goals of the analysis and the need to accurately model the variability in patch windows for effective vulnerability management and risk assessment.

At the core of this correlation lies the concept of vulnerability criticality, which is typically assessed using standardized frameworks such as CVSS (Common Vulnerability Scoring System). CVSS scores range from 0 to 10, with higher scores indicating more severe vulnerabilities. However, these scores are not always directly proportional to the variability in patch-window durations. Instead, they often serve as proxies for the potential impact of a vulnerability, which in turn influences the urgency and effectiveness of vendor responses.

For instance, high-severity vulnerabilities, such as those rated above 9.0 on the CVSS scale, tend to elicit more immediate and coordinated responses from vendors. These vulnerabilities are often associated with critical components of software systems, such as authentication mechanisms or memory management routines. As a result, vendors may prioritize patching these issues to minimize the risk of widespread exploitation. This prioritization can lead to shorter patch-window durations for high-severity vulnerabilities, even though their impact is significant. The variability in patch-window duration for these vulnerabilities is thus influenced by the vendor's ability to quickly identify, validate, and release patches.

Conversely, medium-severity vulnerabilities (CVSS scores between 6.0 and 8.9) often exhibit greater variability in patch-window durations. The variability in their patch-window durations is influenced by several factors, including the complexity of the vulnerability, the availability of resources within the vendor's development team, and the alignment of patching efforts with other product releases. For example, a medium-severity vulnerability in a less-critical component might be deferred until a major release cycle, leading to longer patch-window durations.

The variability in patch-window durations for low-severity vulnerabilities (CVSS scores between 0 and 5.9) is often even more pronounced. These vulnerabilities may not have an immediate or widespread impact, leading vendors to prioritize them lower in their patching schedules. However, the cumulative effect of multiple low-severity vulnerabilities can still pose a significant risk over time. The variability in their patch-window durations is influenced by factors such as the vendor's internal prioritization processes, the availability of resources for testing and validation, and the potential for these vulnerabilities to be exploited in combination with other vulnerabilities.

However, the variability in patch-window durations for high-severity vulnerabilities can still be influenced by factors such as the complexity of the vulnerability and the availability of resources for testing and validation.

In summary, the correlation between vulnerability criticality and patch-window variability is a multifaceted relationship that is influenced by a range of factors, including the nature of the vulnerability, the response mechanisms employed by vendors, and the behavior of the user community. Understanding this correlation is essential for quantifying the variability in patch-window durations across different criticality levels and for developing effective strategies for managing software security risks.

### Temporal Overlap and Concurrency in Multi-Vulnerability Patching

Temporal overlap and concurrency in multi-vulnerability patching are critical factors that influence the overall patch-window duration and variability. When multiple vulnerabilities are addressed simultaneously, the timing of their respective patches can create overlapping periods where some patches are applied before others, or where the application of one patch affects the deployment of another. This concurrency can either reduce or extend the total patch-window period depending on the interdependencies between the vulnerabilities and the coordination among the stakeholders involved in the patching process.

One of the primary mechanisms that contribute to temporal overlap is the synchronization of patching schedules. In many organizations, especially those with large software ecosystems, multiple security teams may be responsible for different components or modules within a system. These teams often operate on staggered timelines, leading to situations where one team completes its patching cycle before another. For example, in the case of the Microsoft Windows operating system, different security teams handle various subsystems such as the kernel, user interface, and networking stack. If the kernel team completes its patching earlier than the networking team, this creates a temporal gap where the networking vulnerabilities remain unpatched until the second team deploys its updates. This staggered approach can lead to extended patch-windows if the teams are not aligned in their release cycles.

Another key factor is the dependency between vulnerabilities. Some vulnerabilities may require patches from multiple components or modules, and the order in which these patches are applied can significantly impact the overall timeline. For instance, consider a scenario where a critical vulnerability exists in both the application layer and the database layer of a software system. If the database patch must be deployed before the application patch to ensure compatibility, this creates a sequential dependency that extends the total patch-window duration. This is particularly relevant in enterprise environments where patching often involves coordinated efforts across different departments or teams.

Concurrency also plays a role in the rate at which vulnerabilities are addressed. In some cases, multiple vulnerabilities may be discovered and reported simultaneously, leading to a surge in patching activity. For example, during the 2017 Equifax data breach, multiple critical vulnerabilities were identified in the Apache Struts framework. The rapid discovery of these vulnerabilities led to a concurrent patching effort by both the vendor and the affected organization. However, the complexity of coordinating across different teams and systems resulted in a prolonged patch-window period, as each vulnerability required its own set of testing, validation, and deployment steps.

The impact of temporal overlap and concurrency is further exacerbated by the presence of multiple stakeholders involved in the patching process. In many cases, the vendor responsible for the software may not have direct control over the patching schedule within the organization that uses the software. This can lead to situations where the vendor releases a patch, but the organization delays its deployment due to internal processes or resource constraints. For example, the 2014 Heartbleed bug in OpenSSL created a significant patch-window issue for many organizations. While the OpenSSL team released the patch quickly, many organizations took weeks or even months to deploy it, leading to extended exposure periods.

Additionally, the presence of multiple vulnerabilities with different severity levels can influence the patching order and timing. In some cases, organizations may prioritize the patching of high-severity vulnerabilities over lower-severity ones, leading to a non-uniform patch-window distribution. This is often seen in enterprise environments where resource allocation is limited, and teams must balance between addressing immediate threats and long-term maintenance. For example, during the 2019 Log4j vulnerability (CVE-2021-44228), many organizations prioritized deploying patches for the most critical systems, while others delayed or deferred less urgent updates, resulting in a mixed patch-window timeline.

The concept of temporal overlap is also relevant in the context of third-party software and supply chain dependencies. When a vulnerability exists in a third-party component used by multiple applications, the patching process can become synchronized across different systems. For instance, the 2021 Log4j vulnerability affected a wide range of applications that relied on the Log4j library. The patching effort required coordination among multiple vendors and organizations, leading to overlapping timelines where some patches were deployed earlier than others. This created a complex patch-window scenario where the timing of updates varied significantly across different systems.

In summary, temporal overlap and concurrency in multi-vulnerability patching introduce significant variability into the patch-window duration. The interdependencies between vulnerabilities, the synchronization of patching schedules, the presence of multiple stakeholders, and the prioritization of certain vulnerabilities all contribute to this complexity. By understanding these factors, organizations can better manage their patching processes and reduce the overall exposure window for vulnerabilities. ### Temporal Shifts and Asynchrony in Vendor Response Timelines

The temporal shifts and asynchrony in vendor response timelines are critical factors that influence the patch-window duration and variability. These phenomena emerge from the inherent complexity of software supply chains, the asynchronous nature of vulnerability discovery and disclosure processes, and the diverse operational models of vendors. Understanding these dynamics is essential for accurately quantifying patch-window metrics and developing robust frameworks for assessing vulnerability management practices.

At the core of temporal shifts is the asynchronous flow of information across the vulnerability lifecycle. Vulnerability disclosures often follow a staggered timeline, where initial reports are made to internal teams, followed by public announcements, and then coordinated disclosure with affected vendors. This process can introduce significant delays between the discovery of a vulnerability and the initiation of vendor response. For example, the 2017 Equifax breach was attributed to a known vulnerability in Apache Struts, which had been disclosed in March 2017. Despite the availability of a patch, Equifax did not apply it until July 2017, leading to a prolonged exposure period. This delay highlights how the asynchronous nature of disclosure and response can extend the patch-window duration, even when a patch is available.

Another key mechanism contributing to temporal shifts is the varying response timelines across different vendors. While some organizations have established, centralized vulnerability management systems that allow for rapid patch deployment, others may rely on decentralized or ad-hoc processes. For instance, in the case of the 2014 Heartbleed bug, which affected OpenSSL, the vendor's response was relatively swift compared to other vendors in the same ecosystem. However, many downstream users and service providers took longer to apply patches, resulting in a prolonged patch-window for those entities. This disparity underscores how the asynchrony between vendor response and user adoption can create variability in patch-window durations across different stakeholders.

The interplay between internal and external timelines further complicates the patch-window metric. Internal timelines are often influenced by organizational structures, resource allocation, and technical debt. For example, large enterprises may have dedicated security teams that prioritize vulnerability remediation based on risk assessments and business impact analyses. In contrast, smaller organizations or those with limited resources may experience delays due to competing priorities or lack of specialized personnel. The 2019 Capital One breach, which exploited a misconfigured cloud server, revealed how internal operational inefficiencies can prolong the patch-window even when external patches are available. This case illustrates how internal timelines can diverge from external disclosure schedules, leading to extended exposure periods.

Additionally, the synchronization between vulnerability disclosures and vendor response timelines is often imperfect. While coordinated disclosure agreements aim to align these timelines, they are not always strictly followed. For example, in the 2018 Meltdown and Spectre vulnerabilities, the initial disclosure was delayed due to coordination among multiple vendors, including Intel, AMD, and ARM. This delay created a ripple effect, as downstream users and service providers had to wait for patches from all affected vendors before implementing mitigations. The asynchrony in these response timelines extended the patch-window duration for many organizations, demonstrating how even well-coordinated disclosure efforts can introduce variability.

The temporal shifts also manifest in the relationship between vulnerability severity and patch deployment speed. High-severity vulnerabilities often receive priority, but this is not always consistent across vendors. For instance, the 2016 WannaCry ransomware attack exploited a known vulnerability in Microsoft Windows, which had been disclosed months earlier. Despite the high severity of the vulnerability, some organizations delayed patching due to operational constraints or lack of awareness. This example highlights how the alignment between vulnerability severity and response timelines can be inconsistent, leading to variability in patch-window durations.

Furthermore, the role of third-party vendors and open-source projects in shaping temporal shifts cannot be overlooked. Many software systems rely on multiple components, each with its own disclosure and response timelines. For example, the 2019 Log4j vulnerability (CVE-2021-44228) affected a wide range of applications and services, including those from major vendors like Apache, IBM, and Salesforce. The patch-window duration for users of these systems was influenced by the speed at which each vendor released updates and coordinated with their customers. This case illustrates how the interdependencies between vendors can create cascading delays, extending the patch-window for end-users.

In summary, temporal shifts and asynchrony in vendor response timelines are multifaceted phenomena that significantly impact the patch-window duration and variability. These shifts arise from asynchronous disclosure processes, varying response timelines across vendors, internal operational constraints, and the interplay between vulnerability severity and patch deployment speed. By understanding these mechanisms, organizations can better quantify patch-window metrics and develop more accurate models for assessing their vulnerability management practices. The examples provided demonstrate how these factors interact to create variability in patch-window durations, emphasizing the need for a nuanced approach to analyzing and mitigating temporal shifts in vendor response timelines.
